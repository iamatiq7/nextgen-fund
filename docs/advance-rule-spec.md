> এই নিয়মই কোডে বাস্তবায়িত (`computeBalance`) এবং ২১টি টেস্ট + emulator E2E দিয়ে যাচাই করা।

## ১. মূল ধারণা

সদস্যের ব্যালেন্স চারটি স্বতন্ত্র বালতিতে ভাগ করা — কোনো একটি "সঞ্চিত" ফিল্ডের উপর নির্ভরতা নেই; প্রতিবার পেমেন্ট লেজার (payments collection) থেকে হিসাব হয়:

| বালতি | অর্থ | সূত্র |
|---|---|---|
| `expected` | আজ পর্যন্ত বিল হয়েছে কত | `monthsInclusive(joinMonth, nowMonth) × monthlyDue` |
| `paid` | মোট verified টাকা (যা হাতেনাতে এসেছে) | `Σ verified (due + advance)` |
| `advance` | বিলের বেশি জমা → অগ্রিম ক্রেডিট | `max(0, paid − expected)` |
| `due` | বাকি (pending সহ) | `max(0, expected − paid − pending)` |
| `pendingDue` / `pendingAdvance` | অনুমোদনের অপেক্ষায় থাকা অংশ | pending টাকার বিভাজন |

**সোনালি নিয়ম:** *প্রতিটি verified টাকা = money received। যা এখন পর্যন্ত বিল হয়েছে তার বেশি = অগ্রিম।*

## ২. নিয়মগুলো (জন্ম / ব্যবহার / বহন / আংশিক)

| প্রশ্ন | নিয়ম |
|---|---|
| অগ্রিম কীভাবে জন্মায়? | (ক) বিলের বেশি `due` পেমেন্ট verified হলে উদ্বৃত্ত অংশ, (খ) সরাসরি `advance` ধরনের পেমেন্ট |
| কখন বিলে সমন্বয় হয়? | মাস পরিবর্তনে `expected` বাড়লে অটো — আগে অগ্রিম খরচ হয়, তারপর নতুন বাকি তৈরি হয় |
| মাস পরিবর্তনে বহন হয়? | হ্যাঁ, স্বয়ংক্রিয়ভাবে খরচ না হওয়া পর্যন্ত বহন করে (আলাদা কিছু লিখতে হয় না) |
| আংশিক পরিশোধে কী হয়? | শুধু যতটা এসেছে ততটা বিল কমে; অগ্রিম ঋণাত্মক হয় না (`due`, `advance` ≥ 0) |
| pending পেমেন্ট? | `due` তাৎক্ষণিক কমায়, কিন্তু `advance`-এ যোগ হয় না যতক্ষণ অ্যাডমিন verify না করেন |
| refund / reject? | verified পেমেন্ট reject হলে `paid`/`advance` আবার হিসাব হয়; ঋণাত্মক কখনো হয় না |
| ফান্ড টোটালে অগ্রিম? | টাকা ফান্ডে এসেছে = `memberDeposits`-এ যোগ; আলাদা `memberAdvance` পুল হিসাবেও দেখানো হয় |

## ৩. লেজার-ট্রেসেবিলিটি

অগ্রিম শুধু একটি হিসাব — **লেজার থেকে পুনর্গঠনযোগ্য**:
`advance = max(0, Σ(verified payments) − monthsInclusive(joinMonth, now) × monthlyDue)`
প্রতিটি পেমেন্টে থাকে: `memberId, memberName, type(due|advance), method, amount, date, ref, status, verifiedBy, verifiedAt`.
